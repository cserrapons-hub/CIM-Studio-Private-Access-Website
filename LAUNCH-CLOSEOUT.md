# Cierre mínimo de CIM Studio — tres formularios

Estado: implementación local en integration/three-forms-2026-10-20. CIM Studio autoriza posteriormente commit/push a integración y el despliegue automático exclusivamente privado, junto con la preparación de una ronda real. Ninguna suscripción ni correo real está autorizado sin una confirmación conjunta adicional de destinatarios/datos/servicios. Main, rama pública, diseño, fotos, logo, tipografías y textos comerciales no se han modificado. Los avisos privados mantienen su aprobación ya registrada y los documentos públicos siguen approved:false.

## Código preparado

- Newsletter privada normal: API v3, campaña PL6jh, njH9fM=['aceptado'], consentimiento D1 firmado/cifrado, Turnstile y deduplicación antes del POST. Una alta nueva no lee el permiso histórico cuando la excepción está apagada; está probado con un parent inválido y permiso antiguo caducado intacto. No crear permisos nuevos ni renovar el anterior.
- Newsletter pública: sustituido el transporte HTML retirado por API v3, comprobación de campaña/double opt-in y contacto existente. El ledger común y el registro API conservan trazabilidad; solo 202 significa aceptación, nunca DOI/Fundadores. Se mantiene newsletterRelease.approved=false: las variables por sí solas no abren captación pública. NEWSLETTER_PROVIDER público deberá ser getresponse-api-v3 tras autorización. No utilizar las instrucciones HTML antiguas.
- Muestras/candidaturas: corregido el redirect:error incompatible con Workers en Turnstile y Resend. Manual y rechazo de 3xx; jamás seguir redirecciones con credenciales/datos. Almacenamiento cifrado separado, consentimiento independiente, mensajes admin/acuse y confirmación/baja laboral ya implementados. Aceptación de Resend no se confunde con entrega. Desconocidos no se reenvían ciegamente.
- Diagnóstico final: solo GET Basic privado, fallback D1 único diagnóstico, estados HMAC y permiso aunque configuración inválida/caducado. No usar este fallback para enviar. Una sola lectura remota bastará para cerrar la incidencia histórica, sin condicionar por ella la prueba de una alta nueva.
- Publicación: corregida la decisión de SEO del build, que dependía de un binding D1 inexistente durante compilación. El build usa aprobación y flags públicos explícitos; el servidor sigue exigiendo binding/credenciales. Privado permanece noindex/no-store y público solo adquiere canonical/robots indexables después de aprobar y activar la versión real.
- Legal público ES/EN: corregida exclusivamente la descripción técnica del formulario propio/API v3 y evidencia D1. No se han aprobado textos, inventado datos o cambiado condiciones comerciales.

## Único bloque remoto que se propone autorizar

1. Commit/push a integration y despliegue automático SOLO en cim-studio-test. Mantener todas las captaciones/envíos desactivados al desplegar; confirmar Basic y endpoint diagnóstico. No tocar proyecto público, permisos, DNS, cuentas o base CIM Production.
2. Un GET al diagnóstico y lectura de su JSON seguro. Si señala formato/disponibilidad, corregir después solo esa variable bajo el mismo alcance expresamente autorizado; no pedir nuevamente secretos/filas. No corregir por conjetura AUDIT_HASH_SECRET ni firmas. La prueba nueva no usa RETRY_PARENT_ID.
3. Con un correo propio nuevo aún no registrado (o alias bajo control del titular, verificado como contacto nuevo por la API), configurar privadamente el HMAC allowlist de ese correo con el secreto independiente existente. No exponerlo en chat/logs/Git. No cambiar AUDIT_HASH_SECRET. Mantener NEWSLETTER_HTML404_RETRY_ENABLED=false y permiso anterior intacto. El usuario conserva dirección y secretos en su entorno.
4. Activar temporalmente únicamente la prueba privada normal de newsletter y las dos pruebas privadas de registros, con sus aprobaciones limitadas ya otorgadas. No aprobar documentos públicos. Comprobar/remediar SOLO variables ausentes que indiquen esos preflights, no repetir auditorías. No cambiar MX/TXT o configuración de correo. No migraciones de producción. Las migraciones 0009/0010 privadas están confirmadas por CIM Studio; esta intervención no requiere nuevas migraciones.
5. Una solicitud newsletter (correo nuevo), una de muestras con los datos ficticios previstos y una laboral para ese mismo correo propio. Verificar D1, GetResponse, doble confirmación, estado antes/después de clicar, campo de consentimiento, admin@cimstudio.es, acuses y confirmación/baja laboral. Resend/Gmail deben demostrar entrega real, no solo estado accepted. Guardar los IDs/evidencias en el inventario privado. Los duplicados y errores se prueban con simulaciones; no repetir envíos reales ante incertidumbre. Una sola ronda conjunta, no una cadena de pruebas separadas.
6. Desactivar todos los envíos privados y conciliar, sin borrar registros. Cierre y limpieza manual según los avisos privados aprobados. Si un proveedor devuelve un resultado incierto, detener y conciliar sin reintentar.

Este bloque incluye solicitudes y correos reales limitados, así que necesita autorización expresa: el trabajo local no los autoriza. No debe activarse la vieja excepción como forma de probar el flujo normal.
