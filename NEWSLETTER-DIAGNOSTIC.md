No renovar ni sustituir el permiso al diagnosticar.

La configuración se inspecciona sin llamar a GetResponse. Solo comprueba presencia/formato de API key y Turnstile, no su validez en el proveedor. La coincidencia entre correo y hash allowlist se comprueba al enviar y no forma parte del enabled actual; este endpoint comprueba el formato del hash y la separación/formato de sus claves, sin descifrar ni pedir emails.

HMAC se verifica con el secreto existente y los campos originales exactos mediante verifyConsentEvidence. No depende de que el permiso siga vigente, de su aprobación ni de que el envío esté habilitado. Errores de una tabla no ocultan la verificación de evidencia cuando la tabla de consentimiento puede leerse. Las consultas son únicamente SELECT parametrizadas con nombres de tabla fijos; sin logs, fetch, rate-limit writes, consumo, renovación o emisión de permisos. Respuesta no-store, noindex y no-referrer. POST devuelve 405, llamadas sin autenticación o fuera del origen privado quedan bloqueadas por la protección existente. No se debe desplegar en proyectos públicos.

El estado permit es independiente de consentHmac: un permiso estructuralmente valid con HMAC invalid nunca acredita elegibilidad ni habilita envíos. Las condiciones que la propia autenticación necesita (origen privado/credenciales/modo privado) pueden bloquear la petición antes de obtener el JSON; no se debilitan para diagnosticarlas.

## Mejora local del identificador, pendiente de publicación

Se conserva RETRY_PARENT_ID_FORMAT y se añaden únicamente nombres estáticos a failedChecks:
- RETRY_PARENT_ID_MISSING y RETRY_PARENT_ID_POSSIBLY_UNAVAILABLE_IN_DEPLOYMENT: context.env devuelve undefined para esa variable. No permite distinguir por sí solo variable no creada, otro ámbito o snapshot de despliegue anterior. No es una afirmación de que se haya usado Preview.
- RETRY_PARENT_ID_TYPE_INVALID: valor no textual.
- RETRY_PARENT_ID_LENGTH_INVALID: no tiene los 36 caracteres exigidos; no se devuelve la longitud real.
- RETRY_PARENT_ID_WHITESPACE_OR_INVISIBLE: contiene espacio, control o carácter invisible/formato Unicode, incluso si no se aprecia en el panel.
- RETRY_PARENT_ID_UUID_STRUCTURE_INVALID: no cumple el patrón hexadecimal con guiones de UUID. Que tenga letras y números no basta: las letras admitidas son A–F, sin distinguir mayúsculas.

No se devuelve el identificador, sus fragmentos, códigos de caracteres, hashes, secretos ni datos personales. No se corrige/recorta el valor ni se cambia el validador del formulario. El identificador inválido nunca se usa como parámetro de selección ni se corrige silenciosamente. La mejora integral descrita después añade una búsqueda alternativa exclusivamente diagnóstica por el único vínculo histórico coherente en D1.

La Function lee el env proporcionado por Cloudflare Pages en onRequest({request,env}); no utiliza process.env ni selecciona entornos por código. En el dominio principal del proyecto debe recibir los bindings/variables del despliegue Production activo. El código no puede verificar que el panel y ese snapshot contienen el mismo valor. Para comprobarlo manualmente, sin revelar valores: proyecto cim-studio-test, ámbito Production, despliegue activo del commit aprobado y estado de guardado/aplicación de la variable. No se deben cambiar variables ni redesplegar para investigar sin autorización. La URL privada y Basic siguen siendo obligatorios; el endpoint no puede ejecutarse en el dominio público.

Validación local de esta mejora: 188 pruebas, incluidos valores ausentes, longitud, comillas, salto de línea, espacios invisibles, guiones Unicode, caracteres no hexadecimales y UUIDs históricos válidos. Todos los indicadores de envío pueden permanecer false. Ninguna operación remota ni uso/renovación del permiso.


## Resolución integral local del bloqueo diagnóstico

Defecto demostrado en el diagnóstico anterior: parentIdValid=false provocaba cuatro lecturas LIMIT 0 y dejaba consentHmac/permit en not_checked, sin examinar los registros existentes. El formato del valor de configuración podía así ocultar el resultado HMAC y la caducidad. La búsqueda diagnóstica queda desacoplada de ese valor cuando su formato es inválido.

La nueva selección cruza newsletter_retry_permits con newsletter_html_deliveries y newsletter_consent_requests por request_id y subject_hash coincidentes, exige HTML rejected/404 y ausencia de newsletter_api_deliveries para ese padre. Incluye permisos caducados; no filtra por la ventana actual para poder investigar el histórico. SELECT ... LIMIT 2 solo permite escoger si hay exactamente un vínculo coherente. Si falta o es ambiguo, se devuelven RETRY_PARENT_D1_LINK_MISSING o RETRY_PARENT_D1_LINK_AMBIGUOUS, con HMAC/permiso not_checked; no se adivina, no se devuelve el número/identidad de candidatos. Los errores de lectura permanecen sanitizados como d1=error. Si el ID configurado tiene formato válido pero apunta a otro registro/ninguno, no se sustituye silenciosamente.

La configuración sigue marcada invalid con sus nombres estáticos originales aunque la selección D1 sea única. El resultado de HMAC puede ser valid/invalid/error independientemente de que el permiso esté expired y de los cuatro indicadores de envío false. El resultado no habilita formulario ni autoriza un permiso. La selección solo existe en server/newsletter-diagnostic.js; el emisor sigue leyendo su ID configurado y mantiene todos los cierres anteriores.

No se ha demostrado incompatibilidad de los UUID generados por crypto.randomUUID ni se ha identificado el valor remoto concreto que causa RETRY_PARENT_ID_FORMAT. Mayúsculas UUID válidas pasan. Valores ausentes, longitud errónea, comillas, Unicode, espacios e invisibles se distinguen únicamente por categorías, sin revelar caracteres. Una comprobación directa de la expresión original en JavaScript confirma que ya rechaza saltos de línea finales; no se ha cambiado el validador operativo ni se atribuye a esa expresión la causa remota. Los tests documentan esa compatibilidad y el rechazo original. No se recortan ni normalizan valores de configuración para el envío.

Comprobación final posterior, si se autoriza desplegar estas mejoras: un solo GET autenticado a /api/controlled/newsletter-diagnostic, con los envíos aún false. Eso basta para obtener el defecto concreto de formato/disponibilidad y HMAC histórico, sin introducir IDs, emails, hashes o secretos manualmente y sin tocar el permiso caducado. Si consentHmac=invalid con enlace único íntegro, no rotar ni reescribir evidencia: conciliar el secreto audit original y los campos firmados. Si valid, no existe un fallo de integridad de esa evidencia en ese runtime. No declarar válida una clave real de GetResponse por este GET: el diagnóstico no consulta al proveedor.

Se cubre solicitud API aceptada/rechazada/incierta, DOI/Fundadores pendientes, doble envío, concurrencia, expiry y fallos de persistencia, sin suscripciones, correo ni D1 remota. No hay nuevo modo simulado en la web pública ni falsas confirmaciones para personas reales.
